# Architecture

## The problem

A refurbished-electronics business buys used devices, grades them, repairs them, runs QC, then sells
each unit on several marketplaces at once. Three things hurt at scale:

1. **Visibility.** Where is every device, and where is stock getting stuck?
2. **Quality.** Nothing may be sold unless it has passed QC.
3. **Overselling.** One physical unit is listed on Back Market, refurbed and Amazon at the same time.
   When it sells on one marketplace, the others must stop selling it at once.

RefurbOps is a small but production-shaped answer to those three problems.

## Layers

```
src/
├── domain/        Pure business logic. No I/O, no framework. 100% unit-testable.
│   ├── types.ts         Device, Stage, Listing, AppState, DomainError
│   ├── pipeline.ts      Stage state machine (allowed transitions + QC gate)
│   ├── qc.ts            QC checklist per device category, grading rules
│   ├── pricing.ts       Suggested price, marketplace fees, profit
│   ├── marketplace.ts   Listing publish + order handling (idempotency, oversell guard)
│   ├── listing.ts       AI prompt, output validation, template fallback
│   ├── service.ts       Use cases: (state, input, now) => newState
│   ├── stats.ts         Dashboard KPIs
│   ├── export.ts        CSV export (escaping, BOM, formula-injection guard), pipeline filter
│   └── seed.ts          Demo data, generated by replaying the real use cases
├── server/        Node-only adapters
│   ├── store.ts         Persistence (JSON file now, Postgres later), serialised transactions
│   ├── ai.ts            Claude API call with timeout + fallback
│   └── http.ts          Error mapping (DomainError → 400), response shape
├── app/           Next.js App Router: thin API routes + page
│   └── api/…            Validate input → call a service → return a snapshot
├── client/        How the UI talks to a backend (interface + 2 implementations)
│   ├── api.ts           Api interface + httpApi (fetch to /api/*)
│   └── demoApi.ts       Same service functions, run in the browser (static demo)
└── components/    React UI (dashboard, pipeline board, device drawer, sync screen)
```

**Dependency rule:** `components → client → (HTTP) → app/api → server → domain`.
`domain` imports nothing from the other layers. This is what makes it possible to run the exact same
business rules on the server *and* in the offline demo, and to test them without a database.

## Key decisions

| Decision | Why | Trade-off / next step |
|---|---|---|
| **Pure-function domain** (`state → newState`) | Easy to test and reason about; no hidden I/O; same code server + demo | Whole-state updates don't scale; with Postgres each use case becomes a SQL transaction (see `db/schema.sql`) |
| **Explicit state machine** for stages | Illegal moves (e.g. RECEIVED → LISTED, manual SOLD) are impossible, not just discouraged | New stages must be added to `TRANSITIONS` (that's the point) |
| **QC gate in the domain**, not the UI | UI bugs or direct API calls can't bypass quality control | — |
| **Webhook idempotency key** `marketplace:orderId` | Marketplaces retry webhooks; a retry must not create a second sale | In Postgres: `processed_webhooks` PK + `ON CONFLICT DO NOTHING` |
| **Serialised writes** (`transact` queue) | Two orders racing for the same unit → exactly one wins | Single-process only. Production: `SELECT … FOR UPDATE` row lock + unique index `one_sale_per_device` |
| **409 for a rejected oversell** | Tells the marketplace to cancel the order, rather than silently accepting it | Needs a cancellation job per marketplace API |
| **AI output treated as untrusted input** | LLMs can invent specs or say "brand new" | Validated by `parseListingResponse`; falls back to a template. AI is never a single point of failure |
| **Seed data generated by replaying use cases** | Demo data can't violate business rules; doubles as an integration test | — |
| **EUR base currency + FX rate snapshot** at intake | Marketplaces sell in EUR, so pricing, profit and stats need one currency. Storing what we paid (`purchase.amount` + `currency`) *and* the rate used means a later rate change never rewrites past margins | Rates are demo constants (`src/domain/currency.ts`). Production: load daily ECB reference rates, cache them, pass them into `addDevice` like `now` |
| **JSON file store** for the demo | Zero setup: `npm i && npm run dev` | Not for production. Swap `store.ts` for Postgres (Drizzle/Prisma), with no change to domain or UI |
| **Atomic file writes** (write tmp + rename) | A crash mid-write can't corrupt the data file | — |

## Request flow: a marketplace order

```
Marketplace ──POST /api/webhooks/orders──▶ route.ts
   validate body ─▶ transact(state => receiveOrder(state, order, now))
                         │
                         ├─ seen marketplace:orderId?   → DUPLICATE (200, no change)
                         ├─ device SOLD / not active?   → REJECTED_OVERSELL (409, logged as error)
                         └─ else → device SOLD, fee + profit recorded,
                                   listing on this marketplace = SOLD,
                                   all other ACTIVE listings = DELISTED (logged)
```

## What I'd add for production

- **Auth + roles** (technician, QC lead, admin); every stage event records the actor.
- **Postgres** using `db/schema.sql`; database constraints back up the domain rules.
- **Real marketplace adapters** behind one interface (`publish`, `delist`, `verifyWebhook`), with HMAC
  signature checks and an **outbox table + job queue** for retries and rate limits.
- **Barcode/IMEI scanning** at intake; label printing.
- **Observability:** structured logs, alerts on oversell attempts and stalled devices (SLA breaches).
- **E2E tests** (Playwright) for the main flows, on top of the existing domain unit tests.
